# Engine view contract

Rules 0.3.9: `getStartSetup(state)` is a pure, day-zero origin-only preview of public initial author stats, job/home costs and time, profile limits, allowed origin choices and an editable first work plan. `configureStart(state,{profile:{penName,message,motive},choiceId,work})` validates the profile, resolves the existing origin and revises the first work atomically. Failure preserves the original state; success stays at day zero with one work and one origin archive entry. Repeated confirmation is rejected. The browser shows this form on first launch, unstarted origin saves, and New Life; an existing life/auto save is replaced only after confirmation and cancellation returns to it. CLI origin choice is unchanged.

User-authored display text lives in `author.identity` (nullable for old saves); seeded penName/motive/paths stay intact. Author views prefer the literal identity and expose `message` separately. `WorkPlan.description` is optional (600 characters); work views expose it as literal text, creation defaults to empty and legacy revisions omitting it preserve the existing value. These strings never enter RNG, ability, aptitude or market calculations. All browser output is escaped. Previous 0.3.8 saves use fixed hash `19918655`, with identity=null and description="" defaults, alongside earlier migrations.

Rules 0.3.8: 300 unique events (299 daily + origin), including 12 follow-ups. Saves through 0.3.7 load by fixed version/hash pairs. Contract event messages now use their actual work ID in the work journal while the event archive retains its contract target. Work-linked state changes (including delayed settlement) are also retained. `dropImpact` reports the actual reputation/stress delta after public resilience and stat bounds, using the same engine operations as the command. Work detail records are copied at command boundaries so adding journal entries never mutates previous states. Mandatory-form title and tag errors are associated with their fields. The existing chapter aggregate rounds to 0.01; tiny positive contributions can remain zero in that older log, a precision limitation handed to Claude rather than a market coefficient change.

Rules 0.3.5: work views add real duration, fractional source/age shares, HOT/BEST exposure, latest retained payout, paid reads, 30 daily quality/schedule observations, and a per-work journal (365 days, at most 200 significant entries). `detail.since/partial` identify records starting after an old save; no historic values are estimated. Schedule stability counts due serial days fulfilled, excludes voluntary hiatus days, and does not count extra chapters twice. First-chapter views come from the chapter log rather than aggregate inflow. `prepareEnding(state,id,remaining)` accepts 1–200 chapters and at least existing stock; it changes the target and multiplies the work's share weight of the existing common plot budget by 1.5. It grants no chapters, quality or completion rewards. The browser exposes this command alongside existing operations and filters significant work history. Saves through 0.3.4 migrate with absent detail records marked partial. `writingSlots` now reads actual writing allocations, rather than job slots.

Rules 0.3.4: `getPendingNewWork(state)` exposes a mandatory request and deterministic `defaultPlan`; `confirmNewWork(state, requestId, plan)` validates the plan and creates exactly one work. Daily event effects are already committed when phase becomes `AWAITING_WORK`, so confirmation never replays them. Event, state and automatic next-work requests on one day merge into the first request. All later automatic works, including a restart after takedown, use this path. The day-zero origin retains its existing first planning work and pre-publication editing screen. The modal permits JSON export, blocks background navigation and cannot be dismissed. Headless drivers explicitly confirm the default plan; `advance` itself always stops. Saves from 0.3.0–0.3.3 load with no pending work.

Source: T-11 and NFR-006/009. All commands accept the current opaque LifeState from the previous result. The browser reads the following selectors.

createLife(seed) returns the day-zero origin choice. advance(state, days) stops before an unresolved choice, returning the new state and stopped reason. choose(state, eventInstanceId, choiceId) closes the pending day or returns an error with the original state. serialize/deserialize round-trip state at day boundaries and choice waits. The web storage adapter owns IndexedDB and file I/O.

Visual development can reproduce the day-zero choice with seed 42 and choose the first option. The implemented browser test advances this same life through day 32 and checks separate work panels. The CLI and engine tests can reproduce longer runs.

## Rules 0.3.1 · player control and integration

- The existing author time policy is expressed in 30-minute slots. `lastPlan` and `lastRoutine` expose the planned and actual totals, and actual `writing` and `plot` allocations are keyed by work ID. A saved policy repeats; the daily total remains 48 slots.
- The day boundary selects and resolves one event, prepares works, applies state behaviors, allocates the shared routine, writes and publishes, updates readership and finance, and records the resulting state. Management commands are rejected while a choice is pending. Editing a control in the browser pauses automatic progression.
- `rushWork` schedules extra releases from stock already written at the beginning of each day. `extraWrite` schedules one additional hour using rest or unused time. The queue is stored in the save, executed once, and reported through `WORK_ORDER` log entries, including a reason for failure. Forced hiatus carries a minimum duration, while voluntary hiatus can be resumed early once health permits.
- `getPlanOptions(state)` includes the three additional tags, their unlock thresholds, and the platform preferences currently visible to the player. New tags and weekly cadences receive hidden aptitudes; `getAptitudeView` continues to reveal only discovery stage and estimate.
- One-time expenses are data-driven in `packages/content/one-time-expenses.v0.json`. The `purchase` command checks current cash and cooldown before recording an immediate `SPEND` ledger entry and applying condition effects. `getLedgerView` returns the last six complete or current 30-day buckets and older carried totals.
- A save from rules 0.3.0 with the same original content is upgraded on load, preserving pending events, queued rushes and career state. Older rule 0.2 saves remain explicitly version-incompatible. The Gemini text override file is retained.
- For the next balance iteration, `Work.prep`, `quality`, `consistency`, `attachment`, `stock`, per-work time allocations and state modifiers are inputs to writing. Reader inflow starts in `readership.ts` through `exposure` and advances through aggregate cohorts in `advanceReaders`. State-specific behavior remains in `states.ts`; user-reported market and long-term balance should be tuned against actual play.

## Rules 0.3.2 · chapter and contract display

- The work detail chart reads `getWorkViews().funnel.rows` directly, with the maximum recorded reads as its scale. The companion list preserves every chapter's reads, drops and rate; a partial migrated log is labelled as starting at `since` and never presented as lifetime history. These values are aggregate expected counts, not individual readers, and cumulative rates can exceed 100%.
- Contract cards display only `getContractViews()` public terms, editor introduction and observed records. Missing historical editor data stays unknown; private company/editor traits remain in the engine. Focusing the chart pauses auto-play for keyboard and scroll access. These changes do not alter rules or saves.
