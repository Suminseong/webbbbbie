# Prototype technical design

Basis: [requirements v0.2](https://app.notion.com/p/422cd7a62697810ca5f8f0b9ed8091e4), [decision record](https://app.notion.com/p/422cd7a6269781ee8de6c0b5a41ebec5) and [T-01–15 / C-01–15](https://app.notion.com/p/422cd7a6269781548033e641dd9c6573). The second Codex assignment approves this scope and keeps the life end policy open-ended.

| Boundary    | Design                                                                                                                                                                                                                                                                                                  | Coverage                                                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Content     | Zod parses JSON for events, platforms, jobs, works, companies, policies and numerical coefficients. New events compose existing conditions and effects.                                                                                                                                                 | NFR-004/009, FR-EVENT-003                                                       |
| Commands    | The engine accepts JSON state and returns a new state. Day 0 only resolves the authored origin choice and creates the first plan. On day D, select from D−1 first, freeze the event and target, then apply effects → time → writing → publication → exposure → readers → economy → transitions → close. | FR-PLAY-001/002/003, FR-TIME-001/002/003                                        |
| Events      | One slot: due follow-up, forced event, regular weighted event, fallback. T-07 cooldown and starvation limits apply. Invalid commands preserve the old state. The player acts through presented choices and clock controls.                                                                              | FR-EVENT-001–005, FR-STATE-001/002                                              |
| Resources   | A 48-slot day allocates work, living, sleep, community, ego search and autonomous writing. Active works share writing in two-slot units based on attachment and stock shortage.                                                                                                                         | FR-LIFE-001/002, FR-WORK-003, FR-WRITE-001/002                                  |
| Market      | Each platform has five age bands, channel and affinity coefficients. Overlapping channels use the bounded union from T-12. Simultaneous works also share the platform pool. Readers advance through five-chapter groups or wait for a new release. Paid eligibility uses a per-work chapter boundary.   | FR-PLATFORM-001–003, FR-READER-001–003                                          |
| Outcomes    | Cash uses integer-won ledger entries, settlements pay accrued amounts once every 30 days. Contract offers are work-scoped with a fixed snapshot. Work endings have a single permanent growth record. Aptitude evidence is separate from actual aptitude.                                                | FR-ECONOMY-001–004, FR-CONTRACT-001–004, FR-GROWTH-001/002, FR-APTITUDE-001/002 |
| Persistence | Versioned JSON saves READY and AWAITING_CHOICE. Keep a compact event archive and persistent eligibility records. Bound verbose logs and daily summaries. UI stores one automatic and three manual slots in IndexedDB and supports portable files.                                                       | FR-SAVE-001–003, NFR-002/005                                                    |
| Browser     | Vanilla TypeScript and Vite provide a functional UI. Only public selectors are used to display the game state. Play/pause, speed, and persistence live outside the engine.                                                                                                                              | FR-UI-001–005, NFR-006/009                                                      |

The engine uses a counter-based 32-bit integer mixer and a stable content fingerprint. The former spike implementation is outside the repository, so the initial product rules version owns its replay fixture. Runtime rules are driven by the adopted coefficients and replaceable JSON. Work lifecycle and money rules are described with the code and tests. The prototype uses 24 daily events and one onboarding event, with the C-09 release target kept in policy data.
